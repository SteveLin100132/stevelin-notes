# 定義與引用範例（二）：設計付款 API

這篇是「定義的使用端」。文中用到的術語都定義在
[定義與引用範例（一）：API 設計術語表](./define-ref-glossary.mdx)，這裡不重寫一次，只用 id 嵌入或引用。
來源筆記之後搬資料夾或改檔名，這裡的引用都不會斷。

## 兩種用法

| 語法                         | 呈現方式                                         | 適合                       |
| :--------------------------- | :----------------------------------------------- | :------------------------- |
| `::include{id="…"}`          | 把整段定義原樣嵌進來，附來源標題與「前往來源」   | 讀者一定要看完的背景知識   |
| `:ref[文字]{id="…"}`         | 行內連結，滑過預覽、點擊固定卡片（手機由底部滑出） | 順帶提到、需要時再看的術語 |

```md
::include{id="api.idempotency"}

付款請求要帶 :ref[冪等鍵]{id="api.idempotency-key"} 才能安全重試。
:ref{id="api.rate-limit"} 省略文字時，顯示定義的 label。
```

- `::include` 是區塊語法，要**單獨一行**
- `:ref` 的 `[文字]` 可省略，省略時顯示定義的 label
- id 找不到、重複、互相嵌入、嵌入過深時 build 會失敗，錯誤訊息附檔案、行號與相近的 id

## 背景：為什麼付款要特別小心

付款是典型「做兩次就出事」的操作。先把冪等性的定義嵌進來：

::include{id="api.idempotency"}

嵌入的內容和來源走同一套渲染，表格與提示框都照常顯示；定義裡的標題也會配合嵌入位置調整層級並列入目錄。

## 設計決策

### 1. 建立付款用 POST，並要求冪等鍵

`POST /payments` 本身不冪等。行動網路斷線、使用者連點按鈕都可能讓同一筆付款送出兩次，
所以要求用戶端一律帶 :ref[冪等鍵]{id="api.idempotency-key"}。伺服器的處理流程直接嵌入來源的步驟說明：

::include{id="api.idempotency-key"}

### 2. 錯誤一律走統一格式

付款失敗的原因很多（餘額不足、卡片過期、重複付款），前端只靠 `code` 判斷分支，
欄位定義見 :ref{id="api.error-format"}。

### 3. 限流與重試

付款端點的限流比一般端點嚴格，超過時回 `429`。用戶端重試前要讀 `Retry-After`，
細節見 :ref[速率限制]{id="api.rate-limit"}。

:::tip{title="怎麼選 include 還是 ref"}
這篇對「冪等鍵」同時用了兩種寫法：第一次提到時用 `:ref` 讓讀者知道有這個詞，
到了真正需要理解流程的段落才用 `::include` 把完整說明嵌進來。
:::
