# LexPayroll 計薪流程知識庫（lexpayroll-payroll-kb）

用 NoteCraftApp 寫的台灣計薪流程學習筆記，讀者是「懂系統、不懂人資」的產品與工程人員。筆記主線是「人員身份 → 出勤 → 加班 → 休假 → 勞健保 → 勞退 → 計薪」，每個知識點都對應到 LexPayroll PL3 的第三層模組代號。

- 完整需求：`CLAUDE_CODE_PROMPT_lexpayroll-payroll-kb.md`
- 寫作計畫與各篇大綱：`PLAN.md`（寫每一篇前先讀對應段落）

## 環境與指令

需要 Node 22 以上（`.nvmrc` 設為 22，使用者的 nvm 預設是 v16）。在 Bash 中執行 npm 或 npx 前，一律先執行 `source ~/.nvm/nvm.sh && nvm use 22`。

```bash
npm run build          # 建置檢查；每篇 commit 前必跑
npm run serve          # 預覽，監看檔案自動 rebuild 並刷新（使用者通常另開 terminal 常駐）
npm run view           # astro dev，可在 UI 上寫入
npm run skill:check    # 檢查 .claude/ 內的 NoteCraft skill 版本
```

建置產物在 `~/.notecraft/cache/<hash>/dist/`，不在專案內。

`npm run view`（astro dev）開著的時候，**不要跑 `npm run build`**。兩者共用 `~/.notecraft/app-<version>/`，build 會清掉 dev server 依賴的 `.astro/`，導致頁面出現「Failed to load url /.astro/content-assets.mjs」。如果已經發生，`touch` 任一篇 mdx 讓 dev server 重新同步內容就會恢復。這時候要驗證，直接看 view 的頁面就好。

## 目錄

```
notes/                      # 筆記（.mdx），slug = 相對路徑去副檔名
.notecraft/components      # @ai-visualize 生成的元件（.tsx）與簡報（.deck.tsx）
.notecraft/components/ui   # 共用 UI：ModuleBadge、KindBadge、Term、glossary.ts、modules.ts
scripts/gen-modules.py      # 從 refs/module-phases.tsv 產生 ui/modules.ts
.notecraft/series.json      # 系列「payroll-101」，00–09 共 10 篇；99-reference 不列入
refs/                       # 產品規劃文件（docx／xlsx），唯讀
refs/module-phases.tsv      # 144 個第三層模組 → 交付階段對照（從分配表 v5 擷取）
.claude/                    # notecraftapp init-skill 安裝的 skill 與 subagent，不要手改
```

注意：生成元件放在專案根目錄的 `.notecraft/components/`，不是 `notes/.notecraft/`。因為根目錄已有 `.notecraft/series.json`，`@notes` 別名會指向根目錄的 `.notecraft/`，放在 `notes/` 底下會建置失敗。
frontmatter 的日期要加引號（`createdAt: "2026-09-24"`），否則 schema 驗證會失敗。

## 讀取 refs/

環境沒有 pandoc，也沒有 python-docx。讀 docx 要用 `zipfile` 解析 `word/document.xml`；讀 xlsx 要在 scratchpad 建 venv 安裝 openpyxl。
- 細化表 v14：8 個第一層、40 個第二層、144 個第三層模組、486 項功能（代號格式 `5.3.2`、`5.3.2-F01`）
- 分配表 v5：階段一 10/31、階段二 11/30、階段三 12/31。可以直接查 `refs/module-phases.tsv`
- 權限矩陣 v2：「功能權限矩陣」工作表逐功能 × 6 權限（查閱／申請／編輯／執行／審核／設定）× 6 角色；L 欄是範圍限制

這些是**產品規劃文件，不是法源**。只能拿來標示模組代號，不得把企業制度或產品規格寫成法律結論。

## 每篇筆記的版型

frontmatter 要有 `title`、`description`、`tags`、`createdAt`。正文依序包含：

1. 一句話重點
2. 這一步的輸入與輸出（表格）
3. 核心規則：每條都附法源（法規名稱＋條號），連到 law.moj.gov.tw 的條文頁
4. 法定 vs 企業制度 vs 系統參數（三欄表格）
5. 算給我看：有數字的例子，要列出算式，並**搭配一個互動元件**（有插圖、讀者可以自己調整或拖動，看數字怎麼算出來）
6. 常見誤解（2–4 點）
7. 對應 LexPayroll 模組：用 `<ModuleBadge code="..." />` 列出
8. 待確認事項
9. 我的問題：放在最後，只寫標題和一行 MDX 註解 `{/* 讀完有疑問就寫在這裡 */}`，內容由使用者自己補，不要代填

免責聲明只放在 00 篇開頭，其他篇不重複。

### 標題層級

NoteCraft 的目錄只收錄 `##` 和 `###`（`###` 可收合在 `##` 底下），`####` 不會進目錄。標題要能讓讀者從目錄直接找到內容。

| 層級 | 用途 | 規則 |
|---|---|---|
| `#` | 不使用 | frontmatter 的 `title` 就是頁面標題 |
| `##` | 版型的 9 段 | 名稱固定，照上面的清單寫，不自創 |
| `###` | 段落內的主題 | 見下方各段的寫法 |
| `####` | `###` 底下的子題 | 只有子題有 3 個以上、而且各自有好幾句說明時才用，例如 01 篇「3. 國籍與居留身分」底下的勞保、職災保險、就保、健保、勞退 |

各段的 `###` 寫法：
- **核心規則**：每條規則一個 `###`，加編號，例如 `### 1. 正常工時`。
- **算給我看**：每個例子一個 `###`，例如 `### 例一：月中到職`，或寫成情境名稱，例如 `### 改成彈性上下班`。
- **互動元件**：放在 `### 互動：…` 標題底下，例如 `### 互動：身分決策樹`，讓元件可以從目錄找到。如果元件本身就在某個例子的 `###` 裡，就不用另外加。
- **待確認事項**：超過 5 項時依性質分成幾個 `###`：`產品範圍`、`需要顧問確認`、`待查證（官方資料）`、`企業制度要先定義`，沒有項目的組別就不列。
- **輸入與輸出**等其他段落：內容有明顯不同的主題時才加 `###`，例如 00 篇的 `### 三種資料性質`。

其他規則：
- **不要用單獨一行的粗體當小標題**，例如 `**1. 正常工時**`，這種寫法進不了目錄，一律改成標題。粗體只用在句子裡強調重點，或用在列點開頭的關鍵字。
- **標題寫成可以搜尋的名詞片語**，要包含關鍵字，例如寫「從屬性怎麼判斷」，不要寫「補充說明」。
- **標題裡不要放連結、`Term`、badge**，目錄只顯示純文字。
- 標題前後都要空一行。

## 正確性規則（最重要）

- 基本工資、投保級距、費率、負擔比例、勞退分級、免稅額、扣繳率等數字，**一律查官方來源**（勞動部、勞保局、健保署、財政部、全國法規資料庫），標註適用期間與查證日期。**不得憑記憶填數字**。查不到就寫 `⚠️ 待查證`，並列進該篇的「待確認事項」。
- 條文用自己的話解釋，不大段照抄。
- 有實務爭議的地方（例如某項給付是否屬於工資），列出不同見解，標為待顧問確認，不自行下結論。

## Badge 與名詞 tooltip

共用元件放在 `.notecraft/components/ui/`，筆記正文和互動元件都用這一套，不要各自手寫：

| 元件 | 用途 | 用法 |
|---|---|---|
| `ModuleBadge` | PL3 第三層模組，顯示代號、名稱、交付階段 | `<ModuleBadge code="3.5.3" />`，只給代號，名稱和階段自動從 `ui/modules.ts` 帶入 |
| `KindBadge` | 資料性質：基礎資料、預定事實、實際事實、確認後結果 | `<KindBadge kind="planned" />`，`kind` 可填 `base`／`planned`／`actual`／`confirmed` |
| `Term` | 專有名詞 tooltip | `<Term k="勞保" />`，要改顯示文字時寫成 `<Term k="投保">加保</Term>` |

規則：
- **模組一律用 `ModuleBadge`**，不要手寫模組名稱或階段。`ui/modules.ts` 是自動產生的，refs 更新後執行 `python3 scripts/gen-modules.py` 重新產生。
- **名詞解釋只寫在 `ui/glossary.ts`**，這是唯一來源，`99-reference/glossary` 也以它為準。新名詞先加進這個檔再使用。解釋寫一兩句白話，不放會逐年變動的數字。
- **每篇筆記的專有名詞，第一次出現時加 `Term`**，後面不用重複加。表格和互動元件裡也可以用。
- MDX 檔在 frontmatter 下方 import：`import Term from '@notes/components/ui/Term'`，其他元件同理。互動元件用相對路徑 `./ui/Term`。
- 不要用 NoteCraft 原生的 `:tip[]{content=""}` 和 `:badge[]` 語法。原因有兩個：解釋內容會散落在各篇筆記裡；原生 tooltip 的定位腳本只在頁面載入時綁定，互動元件重新 render 後產生的 tooltip 不會被定位。`Term` 用的是原生 `.nc-tip` 的樣式，但自己負責定位。
- `ui/` 底下是共用 UI，不是 `@ai-visualize` 產生的元件，所以生成元件可以 import 它們。「生成元件不得互相 import」的限制只適用於生成元件之間。

## 視覺化

- 依 `content-visualize` skill 的流程處理 `@ai-visualize` 標記。視覺風格依 `trendlink-design` skill。
- import 只能用白名單：react、react-dom、motion、recharts、d3、lucide-react、clsx、tailwind-merge。
- 元件不可有 required props、不可使用 emoji、不可自帶外框卡片。外框由 `GeneratedFrame` 提供。
- 費率、級距、上限等數字集中在元件頂部同一個設定物件，並標註 `effectiveFrom` 與 `source`，不要散落在 JSX 裡。
- 元件內的文字一律用 `div`／`span`，不要用 `p`、`ul`、`li`、`h1`–`h3`、`table`。筆記頁面的 `.nc-prose` 樣式會覆寫這些元素的字級與間距，Tailwind 的 `text-sm` 會失效，造成跑版。
- 內容區最寬約 760px，手機約 290px。元件不能靠橫向捲動撐版面，交付前要在瀏覽器用桌面與 mobile 兩種寬度檢查。
- 使用者要「圖文並茂」：除了互動之外，要有手繪 SVG 插圖（場景、物件），不能只放 icon。插圖用 `var(--blue-*)`、`var(--orange-*)`、`var(--neutral-*)` 上色。SVG 動畫的縮放原點用 `transformBox: "view-box"` 加上明確座標，旋轉用靜態 `transform` 屬性，否則位置會跑掉。
- 簡報用 `content-present` skill，產出到 `.notecraft/components/<slug>.deck.tsx`。

## 工作方式

- 一次完成一篇：撰寫 → 查證數字 → 處理 `@ai-visualize` → `npm run build` → commit。
- commit 訊息格式：`docs(payroll-kb): 03 加班費`
- 每完成一篇，用三到五句話回報這篇的重點與待查證項目。
- 使用者以繁體中文溝通，筆記一律使用台灣用語與全形標點。
